# PRD-001: quotient — delegation under operator authority

<!-- Reference forms: `lib:reference/glossary.md` § reference forms. -->

## 1. Intent

An agent such as Claude Code or Codex spends its own, expensive context on
everything it does, including work that needs no judgement: recon across many
files, a first-pass review, a mechanical edit. That work could go to a cheaper
model running in pi. Calling pi directly gives the agent no confinement (a
delegate can read and write whatever the user can), no usable signal (nothing
until it ends, or a verbose event stream), and no way to run, queue or cancel
several delegations.

quotient is a stdio MCP server that closes that gap. The calling agent starts
pi runs, waits on them, and reads back a compact account of each. The
operator — the human who installs and configures quotient — decides, in
configuration no confined delegate can write, where delegates may work, which delegate
profiles exist, how much each run may spend, and what confines it.

Desired end state: an agent delegates routinely and cheaply, the operator
trusts that no delegate can exceed what was granted or rewrite the record of
what it did, and neither needs a skill, plugin or bespoke prompt to get there.

Three actors recur throughout:

- **Calling agent** (the orchestrator): chooses the task, profile, root and
  narrower limits per call; reads results; keeps judgement and verification.
- **Operator**: writes the policy and profiles, approves project forms,
  chooses the forms. Holds all authority; the calling agent holds none it was
  not granted.
- **Delegate**: the pi process a run starts. It is untrusted: it may try to
  widen its own powers, choose what confines it, or edit its own record.

### Terms

These terms are used, undefined, by every spec beneath this one.

- **MCP** (Model Context Protocol): the JSON-RPC protocol an agent's harness
  uses to call tools. quotient speaks it over stdio.
- **pi**: the coding-agent program a run executes. quotient launches it; it
  does not ship it.
- **Run**: one task given to one pi process, from admission to its result.
- **Root**: the directory a run works in (the call's `cwd`). The operator
  allowlists the roots runs may use.
- **Profile**: an operator-written file naming a delegate's model, thinking
  level and tools, and the filesystem **capability** it needs: `read` (the
  root is read-only) or `write`.
- **Policy**: the operator's one configuration file. It allowlists roots and
  profiles, pins each profile's capability, sets per-run limits, and names the
  form for each capability.
- **Form**: an executable that confines one pi process, for example a sandbox
  launcher. The policy names a **machine form** per capability; a project may
  supply its own **project form**, which runs only once the operator has
  **approved** that exact file.
- **Session**: pi's conversation state, kept so a later run can continue it.
- **Lane**: a named queue in which runs execute one at a time, in start order.
- **Evidence**: the files a run leaves behind — its event stream, audit trail
  and result.

## 2. Scope

In scope:

- Delegating one bounded task per run, with a reduced account as the answer.
- Running several delegations concurrently, in ordered lanes, and cancelling
  them.
- The operator's configuration: policy, profiles, approvals of project forms,
  overridable help.
- The contract a confining executable (a *form*) must meet, and how a form is
  selected for a run. Building forms is the operator's concern; quotient
  documents one way to build them.
- Durable evidence of each run and each refused attempt.
- Self-explanation to the calling agent and the operator.
- The stand-alone reducer.

Out of scope:

- Confinement itself. quotient selects and launches a form and checks what it
  can of the child's view; the form does the confining.
- Choosing, hosting or brokering models and credentials. pi is a
  prerequisite, not a dependency; a model broker is optional.
- Judging the quality of a delegate's work. Verification stays with the
  calling agent.
- Bounding the number of runs in flight (see §6 Non-guarantees and OQ-4).
- Multi-host coordination. Servers may share a run directory on one host; a
  run owned by a server on another host cannot be judged lost.

Boundaries:

- One run, one pi process, one root. Work that needs two trees is two runs.
- Authority is whatever the operator's configuration grants at the moment a
  run is admitted or launched. Nothing a delegate writes enters that
  configuration.

## 3. Principles

- **The delegate is untrusted.** Every input that decides a run lives where no
  confined delegate can write it, and the run's evidence is out of its reach.
- **The operator's word is never downgraded.** A configuration quotient does
  not fully understand refuses; it is never read as the nearest thing quotient
  does understand.
- **Fail closed, first failure wins.** What cannot be established refuses, and
  the refusal names the first check that failed.
- **A caller can only narrow.** Per-call limits, tools and budgets may tighten
  what the operator granted, never widen it.
- **Approval is selection.** A project's own form runs only as the exact
  identity the operator recorded; there is no fallback to something else.
- **State lives on disk, not in memory.** A published terminal status reads
  the same from any server, before and after any server exits.
- **Say what is not guaranteed.** Every limit of the guarantees is stated where
  an operator will read it, not left for them to discover.
- **The tool explains itself.** Guidance ships with the binary and reaches the
  agent through the protocol; no skill is required to use it well.

## 4. Requirements

The functional and quality requirements this capability must satisfy are
recorded as requirement entities and appear under the synthesized Requirements
section below. This section carries only the constraints and invariants that
bound every valid implementation.

Constraints:

- quotient is a stdio MCP server; the client owns its lifetime through stdin.
- pi is invoked as an external program; quotient does not embed or fork it.
- quotient ships no forms. A form is the operator's choice; quotient defines
  what a form must guarantee and stays agnostic of how a form achieves it
  (a jail, a platform sandbox, or a hand-written launcher).
- Configuration that decides a run is read from the operator's configuration
  location only, never from the project tree a delegate works in.
- Every machine interface a client or operator tool depends on — the
  documents tool calls answer with, the policy, the approvals store and the
  form invocation — is a versioned, shipped contract. Profiles follow a documented grammar without a
  version; help, transcripts, diagnostics and the evidence logs are not
  versioned interfaces.
- Shipped text (docs, help, examples, README) is self-contained: it cites no
  internal planning identifiers.

Invariants:

- Under a form that meets the form contract, nothing a delegate writes can
  raise any run's powers or alter any run's evidence. An unconfined form gives
  this up (§6).
- A run admitted again at launch can be refused or narrowed, never widened,
  and keeps the root, session and capability it was admitted with.
- A root governed by an operator approval runs exactly the approved form
  identity or refuses.
- Once a run's terminal status is published on disk, it never changes.
- No run outlives an orderly shutdown of the server that started it. If the
  server dies abruptly, a confined run dies with it by the form's promise; an
  unconfined run does not.
- Every way a running run stops goes through one termination path and one
  audit record.

## 5. Success Measures

Outcomes:

- An agent configured with only the MCP server sets quotient up, delegates,
  and orchestrates many runs from quotient's own help, with no skill or
  prompt file.
- Delegated runs cost materially less than the calling agent doing the same
  work, at quality the calling agent's verification accepts.
- The operator can answer "what did that run do, under what grant?" from the
  evidence alone, after the fact.

Signals:

- Refusals are resolved by the indicated party (caller or operator) without
  reading source code.
- No observed run exceeds its grant: no write outside its writable set, no
  run under a capability or form the operator did not choose.
- Runs stopped short are continued through their session rather than
  restarted.

Acceptance gates:

- The release gate (`just gate`) is green: unit tests, contract drift tests,
  and form-family checks.
- The shipped contracts match the implementation in both directions
  (refusal reasons, result fields and states, policy keys, approvals format).
- The write-denial probe passes against each form the project ships guidance
  for.

## 6. Behaviour

**Delegate one task (blocking).** The calling agent calls `pi_agent` with a
prompt, a profile and optionally a root, session, tools and tighter limits. The
call is admitted against the policy, the profile's capability pin, the root
allowlist, the form selection, the limits, the session and the child's view.
Admitted, the run launches pi inside the selected form, is bounded by its
limits, and settles with a result. A client that declares MCP tasks receives a
task at once and polls it instead of blocking.

**Delegate several (non-blocking).** The agent starts each run and gets a
handle at once; a `key` makes a retried start answer the same run. It waits on
named handles for any or all to settle, within a timeout, receiving results
within a byte budget. A wait changes nothing, so to collect results that did
not fit, the agent drops the ids it has consumed and waits again. A run
given a lane waits for the run started before it in that lane to settle;
`needs_success` refuses it if that predecessor did not complete, and the
refusal cascades. Queued runs are admitted again when they launch.

**Recover lost handles.** A wait naming no runs reports every started run no
one has acknowledged; acknowledging a used run removes it from that list.

**Cancel.** Cancelling marks a run before anything is awaited, so a lane never
launches a run about to be cancelled. A queued run settles without launching;
a running run is stopped through the one termination path. A run that
completes before the stop reaches it reports completed.

**Continue.** Naming a previous run's session continues that conversation, in
the same root and capability. A busy session refuses.

**Refusal.** Any failed check answers with a refused result naming the first
failed check. Nothing ran. The calling agent decides from the reason whether
to change the request, retry later, or tell the operator.

**Operator setup.** The operator writes the policy (roots, profiles and their
capabilities, limits, forms), installs profiles, and approves any project
form by hash. Without a policy every call that would start a run refuses. The policy and approvals
apply from the next call; profile and help changes apply at the next server
start.

**Client goes away.** Stdin closing or a signal stops reading, stops every
running run, settles every queued one without launching, and answers nothing
further. Each run still records its outcome.

**Recovery across servers.** Any server sharing the run directory answers for
a run another server, or an earlier process, started: settled from its result,
lost only on positive evidence, otherwise still working. One exception: when
the run directory itself becomes unwritable, the owning server reports the run
lost while other servers read it as still working until the owner is confirmed
dead.

Non-guarantees (stated, not hidden):

- The form does the confining; quotient's check of the child's view is only
  as sound as the form's promise.
- An approval's digest covers the form's bytes only.
- A root or `cwd` spelled through a symlink a delegate can rewrite is
  governed where it lands.
- Limits are enforced after each request, so a run can overshoot by the
  request that crossed a limit; the wall clock is the hard backstop.
- There is no bound on runs in flight; concurrency multiplies spend.
- Waits that name no runs are per server, not per caller.
- A run owned by a server whose death cannot be judged reads as working
  until its result lands.
- An unconfined form gives up every confinement guarantee, including that
  the run dies with the server.
- Stopping a run signals the process group the form started in. A form that
  moves processes out of that group escapes cancellation and shutdown; the
  form contract does not yet forbid it (ISS-004).

## 7. Verification

Behaviour is proven at three levels.

Contract conformance is mechanical: drift tests hold each shipped contract and
the implementation equal in both directions (refusal reasons, result fields
and states, the cause-to-state table, policy keys and environment variables,
the approvals format), and reject internal identifiers in shipped text. These
carry REQ-008 and REQ-015.

Behaviour is proven by tests against a scripted stand-in for pi, covering
admission order and fail-closed refusals (REQ-004, REQ-006, REQ-007, REQ-012),
lane order and cancellation (REQ-002), protocol eras and tasks (REQ-003),
shutdown (REQ-014), and recovery of runs from disk across servers (REQ-010,
REQ-013).

Confinement is proven against real forms: form-family checks read built
launchers and refuse those that break the form contract, and the write-denial
probe samples the form's promise from inside a run (REQ-005). These sample the
promise; they do not prove a form sound, and §6 says so.

Self-explanation (REQ-009) is reviewed: a fresh agent given only the server
completes setup and a delegation from quotient's help. Cost and quality of
delegation (§5 Outcomes) are judged by the operator from run evidence, not
gated.

## 8. Open Questions

- OQ-1 — Does a profile carry standing instructions to its delegate, beyond
  configuration? Today the profile body is notes for humans and the caller's
  prompt is the delegate's only instruction. Blocks the profile's product
  definition in the Config and profiles spec; that spec must leave the body's
  role open. (Backlog: IMP-012.)
- OQ-2 — Should a refusal point the calling agent to the help that resolves
  it (setup for a missing policy, the policy reference for an invalid one)?
  Affects REQ-008's acceptance and whether the refusal envelope grows a
  field. (Backlog: IMP-013.)
- OQ-3 — What should a running run report while it works, and to whom: the
  calling agent deciding whether to cancel, or the operator watching spend?
  Blocks any in-flight fields on the run document; such fields must be
  additive. (Backlog: IDE-007.)
- OQ-4 — Should the operator be able to bound the number of runs in flight?
  Today it is a stated non-guarantee. (Backlog: IDE-005.)
- OQ-5 — Which platforms get documented form guidance beyond Linux with Nix
  (macOS Seatbelt; a hand-written form)? The form contract stays
  backend-agnostic regardless. (Backlog: IMP-008.)

## Requirements

### FR-001 (REQ-001) — Delegate a bounded task and receive a reduced account

delegate-a-bounded-task-and-receive-a-reduced-account · functional · pending

A calling agent can hand one bounded task to a pi delegate, naming a prompt, a profile and a root, and receive a reduced account of the run: a budgeted transcript, a status (usage, cost, request-context peak, counts) and a verdict saying whether it succeeded and, if not, why.

acceptance criteria:
  - A run started with a prompt and an allowed profile settles with a result carrying transcript, status and verdict.
  - The verdict distinguishes success from every way a run can stop short, and names the cause.
  - The transcript is cut to a byte budget the operator sets and the caller may only lower; the final answer is always kept whole, so a long answer can exceed the budget, and a budget of zero disables cutting.

### FR-002 (REQ-002) — Run several delegations at once, or in order

run-several-delegations-at-once-or-in-order · functional · pending

A calling agent can start runs without blocking, wait on any or all of them, cancel them, and queue runs in a named lane so they execute strictly in start order, optionally only after the predecessor succeeded.

acceptance criteria:
  - A start answers at once with a handle; a wait over several handles answers when any or all have settled, or when its timeout passes.
  - Runs in one lane launch one at a time in start order; a run that requires its predecessor's success is refused when the predecessor did not complete.
  - A cancelled run settles with a cause, whether it was queued or running.

### FR-003 (REQ-003) — Clients with and without blocking tolerance are both served

clients-with-and-without-blocking-tolerance-are-both-served · functional · pending

quotient serves clients that can wait on a long call, clients that abandon long calls, and clients that poll MCP tasks, without the operator configuring which kind a client is.

acceptance criteria:
  - A client that declares MCP tasks receives a task from the blocking tool and can poll it to its result.
  - A client without tasks can start and wait in calls each shorter than its tool-call timeout.
  - A legacy client keeps working unchanged regardless of how other clients of the same server speak.

### FR-004 (REQ-004) — Operator holds all authority over what a delegate may do

operator-holds-all-authority-over-what-a-delegate-may-do · functional · pending

The operator alone decides, in configuration no confined delegate can write, which roots a run may work in, which profiles exist and what capability each has, the per-run limits, and what confines each capability.

acceptance criteria:
  - A run in a root outside the operator's allowlist is refused.
  - A profile whose declared capability differs from the operator's pin is refused.
  - No configuration that decides a run is writable from inside a run confined by a form that meets the form contract.

### FR-005 (REQ-005) — Every run is confined by an operator-chosen form

every-run-is-confined-by-an-operator-chosen-form · functional · pending

Every run executes inside a form, an executable the operator chose per capability that decides what the delegate can read and write; a project may supply its own form only once the operator has approved that exact executable.

acceptance criteria:
  - A run launches only through the form selected for its capability and root.
  - A project-supplied form runs only when its real path and content digest match an operator approval; otherwise the run is refused, never run with a different form.
  - Running pi with no confinement requires an explicit, separately named operator choice.

### FR-006 (REQ-006) — Per-run limits the caller can only narrow

per-run-limits-the-caller-can-only-narrow · functional · pending

Each run is bounded by operator maxima on requests, per-request context, cost and wall clock; a caller may ask for tighter limits for one run but never looser ones.

acceptance criteria:
  - A caller limit above an operator maximum is refused, not clamped.
  - A run that crosses a limit is stopped and settles with that limit as its cause.
  - The wall clock stops a run that has gone quiet.

### FR-007 (REQ-007) — Continue a delegate's conversation

continue-a-delegates-conversation · functional · pending

A caller can continue a previous run's conversation by naming its session, within the same root and capability the session was first used with.

acceptance criteria:
  - A run naming a settled session continues that conversation.
  - A session cannot be continued in another root or under a wider capability.
  - A session in use by another run is refused, not shared.

### FR-008 (REQ-008) — Refusals are verdicts the agent can act on

refusals-are-verdicts-the-agent-can-act-on · functional · pending

Every refusal, from any tool, is an ordinary result naming the first check that failed and a detail for the operator, so a calling agent reads it like any other verdict and can tell whether a retry, a different request, or the operator is needed.

acceptance criteria:
  - A refused call answers with a result whose state is refused and whose reason is one of a documented closed set.
  - Each documented refusal reason states what it means, and whether the request alone can clear it or the operator must act.
  - A refusal is never delivered as a protocol error.

### FR-009 (REQ-009) — quotient explains itself to the agent using it

quotient-explains-itself-to-the-agent-using-it · functional · pending

Everything a calling agent needs to set up, delegate, read results and orchestrate many runs ships with the binary and reaches the agent through the server's own instructions, tool descriptions and a help command; no skill or prompt file is required. The operator can override any help section.

acceptance criteria:
  - An agent with only the MCP server configured can find setup, delegation and orchestration guidance from the server and `quotient help`.
  - Help shipped with a version describes that version.
  - An operator override of a help section replaces that section for both the agent and the human reader.

### FR-010 (REQ-010) — Every run leaves durable evidence

every-run-leaves-durable-evidence · functional · pending

Each admitted run keeps an evidence directory with its event stream, audit trail and settled result, outside the reach of any delegate confined by a form that meets the form contract; any server sharing the run directory can answer for a run another server or an earlier process started.

acceptance criteria:
  - A settled run's result is readable from its evidence directory after the server that ran it has exited.
  - Attempts that spawned nothing are recorded with what was asked and why it was refused.
  - A delegate confined by a form that meets the form contract cannot alter its own run's evidence.

### FR-011 (REQ-011) — Reduce a pi event stream on its own

reduce-a-pi-event-stream-on-its-own · functional · pending

An operator or tool can turn a pi JSON event stream into the same transcript and status a run's result carries, without running the server.

acceptance criteria:
  - `quotient reduce` over a pi `--mode json` stream produces the transcript and status a run of that stream would report.

### NF-001 (REQ-012) — Fail closed

fail-closed · quality · pending

Anything quotient cannot read, resolve, recognise or record refuses the run; nothing unknown or unreadable is ever read as permission, and an unknown configuration field refuses rather than being ignored.

acceptance criteria:
  - An unreadable or malformed policy, profile directory or approvals store refuses every affected call.
  - A configuration field quotient does not recognise refuses rather than being dropped.
  - When admission checks fail, the first failing check in a fixed order is the reported reason.

### NF-002 (REQ-013) — A settled status never changes

a-settled-status-never-changes · quality · pending

Once a run's terminal status (settled or lost) is published on disk, every later report from any server reads the same; a run is reported lost only on positive evidence that no result can still arrive. One exception: when neither the result nor the loss record can be written, the owning server reports the run lost while other servers read it as still working until the owner is confirmed dead.

acceptance criteria:
  - A run's settled status is identical before and after the reporting server exits.
  - A run whose owner cannot be judged dead reads as still working, not lost.
  - A run whose result and loss record both fail to write reads lost from its owner and still working from another server until the owner is confirmed dead.

### NF-003 (REQ-014) — No run outlives the server's shutdown

no-run-outlives-the-server · quality · pending

When the client goes away or the server is signalled, every running run is stopped through one termination path, every queued run settles without launching, and each records its outcome. The stop reaches every process that stays in the run's process group; keeping the delegate in that group is the form's obligation.

acceptance criteria:
  - After the client closes stdin, no process remains in any of that server's run process groups.
  - Each run stopped by shutdown records a result naming the shutdown as its cause.

### NF-004 (REQ-015) — Shipped contracts are versioned and kept true

shipped-contracts-are-versioned-and-kept-true · quality · pending

Every machine interface a client or operator tool depends on (the documents tool calls answer with, the policy, the approvals store and the form invocation) has a versioned, shipped contract; a change that would break a reader takes a new version, and the shipped contracts are checked mechanically against the implementation. Profiles, help text, transcripts and evidence logs are outside this requirement.

acceptance criteria:
  - Each quotient document (result, run handle, wait answer, ack answer), the policy and the approvals store carry a schema field naming their version; MCP task responses and protocol envelopes carry none, and the form invocation is versioned by its contract's name (form-1).
  - Contract text and implementation are checked against each other on every release gate.
